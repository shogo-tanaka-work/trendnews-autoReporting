## B. 取得キーの準備

| キー | 必須度 | 取得先 / メモ |
|---|---|---|
| `GITHUB_TOKEN` | 実質必須 | fine-grained token で **Public repositories (read-only)** のみ。未設定だと 60 req/h に当たり `tech_web` / `tech_ai` が途中で 403 になる |
| `YOUTUBE_API_KEY` | `tech_youtube` に必要 | Google Cloud で YouTube Data API v3 を有効化。未設定なら `tech_youtube` だけがエラーになり、他カテゴリは正常に動く |
| `ADMIN_TOKEN` | 任意 | 16文字以上。未設定だと `POST /admin/collect` は 503 で無効化（fail closed） |
| Slack チャンネル4つ | 通知に必要 | `#tech-cloud` `#tech-web` `#tech-ai` `#tech-youtube` 等を作り、Bot を招待して ID を設定する |

チャンネル未設定のカテゴリは**収集だけ行い通知をスキップ**する。未通知記事は
`notified_at IS NULL` のまま溜まり、チャンネル設定後の初回実行で
`minScore` / `maxPerSource` で絞られた分だけ通知され、残りは処理済みになる。
つまり後から設定しても大量投稿にはならない。

## C. ミニ PC でのデプロイ

手順は [README.md の「Ubuntu ミニ PC へのデプロイ」](../README.md#ubuntu-ミニ-pc-へのデプロイ) をそのまま実行する。要点だけ:

1. Node.js 20 以上（動作確認は 24）。`better-sqlite3` を native build するので `build-essential` と `python3` が要る。
2. 秘密情報は `.env` ではなく **`/etc/tech-radar/environment`**（root:techradar / 0640）に置く。
   systemd の `EnvironmentFile=` がこれを読む。
3. `npm run gen:systemd` → `systemd/generated/` の drop-in を `/etc/systemd/system/` へ配置。
   スケジュールの正本は `src/config/categories.ts` の `schedule` で、unit 側に時刻を書かない。
4. タイマーは `tech-radar-collect@<category>.timer` をカテゴリごとに enable する。

### 動作確認の順番

```bash
# 1. 単発で収集できるか（DB とネットワーク）
sudo -u techradar node /opt/tech-radar/dist/jobs/collect.js tech_cloud

# 2. 2回目で new_count が 0 になるか（重複排除）
sudo -u techradar node /opt/tech-radar/dist/jobs/collect.js tech_cloud

# 3. systemd 経由
sudo systemctl start tech-radar-collect@tech_cloud
journalctl -u tech-radar-collect@tech_cloud --since "5 min ago"

# 4. タイマーが登録されているか
systemctl list-timers 'tech-radar-*'

# 5. API
curl http://127.0.0.1:3000/health
curl 'http://127.0.0.1:3000/articles?category=tech_cloud&limit=5'

# 6. 実行履歴
sqlite3 /opt/tech-radar/data/tech-radar.sqlite \
  'SELECT job_name, status, new_count, error_message FROM job_runs ORDER BY id DESC LIMIT 10;'
```

### つまずきそうな点

- **`ProtectSystem=strict`** を入れているので、`data/` 以外へ書こうとすると Read-only file system になる。
  DB の場所を変えるなら unit の `ReadWritePaths=` も直す。
- **`Type=oneshot` では `Restart=` が使えない**。収集の失敗は次回のタイマー起動で再試行される
  （未通知キュー方式なので、失敗した通知も自動で再送される）。
- **SQLite は WAL + busy_timeout 5s**。カテゴリごとに実行時刻をずらしてあるので通常は競合しないが、
  スケジュールを変えるときは時刻が重ならないようにする。

## E. 今回の設計変更で覚えておくこと

1. **重複排除は DB でやる**。旧 `FILTER_HOURS`（発行時刻が N 時間以内か）は廃止した。
   `UNIQUE(source_id, external_id)` + `notified_at` で判定する。
2. **通知対象は「未通知の全件」**。今回挿入した分だけを見ると Slack 送信失敗が再送されないため、
   毎回 `articles.listPending(category)` を引き直す。
3. **Collector は Hono も systemd も知らない**。CLI と `POST /admin/collect` が
   同じ `collectAll()` を呼ぶ。Workers へ移すときは `scheduled` から同じ関数を呼べばよい。
4. **Node 依存は `lib/env.ts` と `db/` だけ**。`process.env` を他所で読まない。

## F. 情報源の増やし方

`src/config/categories.ts` に1行足すだけ。

```ts
{ id: 'gh-drizzle', type: 'github', name: 'Drizzle ORM', repo: 'drizzle-team/drizzle-orm', emoji: ':droplet:' }
```

（`minScore` 未満は通知しない）。既存カテゴリは全件通知のまま。
